The Chartroom · kubectl and the triage flow

Logs, and the logs from before the crash

When a pod crashes, the Keep gives it a fresh start, a bit like a console session that was closed and opened again. The new session's screen is blank. Adding --previous asks for the screen from the session that closed, which is where the bad news was written.

When a container exits, it is restarted in place inside the same pod. kubectl logs shows the container running now, which may be only seconds old and have said nothing useful. kubectl logs --previous shows the output of the one that last terminated. For a pod in CrashLoopBackOff, that is where the reason lives.

The node keeps the log file of the current container and of the one before it, one generation back, for each container in the pod. Each restart bumps the restart count and lengthens the back-off, from 10 seconds up to a 5 minute cap. Those files live on the node, so when the pod is deleted or lands on another node, --previous has nothing to show. That gap is why clusters ship logs somewhere durable, such as Loki, which you'll meet in Signalwood.

Then → Now

Then · the Console Room tail -f /var/log/messages One box, one log. You watched it scroll, and yesterday's lines were still on the disk.
Now · the Reach kubectl logs --previous The box is replaced on every crash. You ask for the log of the one that fell, not the one that got back up.
